# MOSAIC — برومبت البناء الكامل

## نظام ذكاء اصطناعي للتعلم المستمر والتطور الذاتي والتعلم من النماذج الأخرى

> انسخ هذا البرومبت كاملًا وأعطه لوكيل البرمجة (Claude Code أو غيره) أو لفريق التطوير.

---

## 0. دورك ومهمتك

أنت مهندس أنظمة ذكاء اصطناعي أول. مهمتك تصميم وبناء **MOSAIC**: نظام ذكاء اصطناعي يتعلم باستمرار ويتطور ذاتيًا بطريقة قابلة للقياس. يكتسب المعرفة والمهارات والأدوات والاستراتيجيات، ويتعلم من البشر ومن **نماذج الذكاء الاصطناعي الأخرى**. لا يعتمد على إعادة برمجته يدويًا في كل مرة، ولا يعتمد قدرة جديدة قبل اختبارها.

MOSAIC ليس تطبيقًا يضع نموذجًا لغويًا ثابتًا فوق ذاكرة محادثات. هو بنية تعلم كاملة. النموذج اللغوي فيها مكوّن واحد قابل للاستبدال.

### معنى "لا محدود التعلم" في هذا المشروع

- **لا سقف برمجيًا ثابتًا**: لا يوجد في التصميم حد مكتوب مسبقًا لعدد المهارات أو الأدوات أو مجالات المعرفة أو اللغات أو النماذج المعلّمة.
- **قابلية توسع أفقية**: يجب أن تنمو كل وحدة (الذاكرة، المهارات، الأدوات، النماذج) بإضافة سجلات أو وحدات، دون إعادة كتابة النظام.
- **صدق في الحدود**: الموارد الحسابية والتخزين والبيانات والطاقة محدودة فعليًا. لا تَعِد بذكاء أو موارد غير محدودة. النظام يدير هذه الحدود بذكاء ولا يتجاهلها.

### المبادئ الحاكمة (غير قابلة للتفاوض)

1. **كل ادعاء بالتحسن يحتاج دليلًا قابلًا للتكرار.**
2. **لا تعديل مباشر في الإنتاج دون اختبار في بيئة معزولة.**
3. **كل تغيير له إصدار وقابل للتراجع.**
4. **الخصوصية والموافقة أولًا**: لا رفع ولا مشاركة ولا تدريب مشترك على بيانات المستخدم دون موافقة صريحة.
5. **سجّل نوع التغيير بدقة**: إضافة معلومة إلى قاعدة البيانات ليست "النموذج أصبح أذكى".
6. **لا دورات بلا فائدة**: كل دورة تعلم لها ميزانية وهدف قابل للقياس وشرط توقف.

## 1. البنية العامة

ابنِ النظام من وحدات مستقلة تتواصل عبر واجهات (Interfaces) محددة. لا تربط منطق التعلم بأي واجهة مستخدم.

```
┌──────────────────────────────────────────────────────────────────┐
│                     واجهات المستخدم (Android أولًا)               │
│            Chat UI · Evolution Dashboard · Approvals · Settings   │
└───────────────────────────────┬──────────────────────────────────┘
                                │  MOSAIC Core API
┌───────────────────────────────┴──────────────────────────────────┐
│  Orchestrator  ←→  Task Executor  ←→  Strategy Selector           │
├──────────────────────────────────────────────────────────────────┤
│  Continual Learning Engine   │  Evolution Lab (Sandbox)           │
│  Multi-Model Learning Hub    │  Regression & Forgetting Guard     │
│  Human Feedback System       │  Resource-Aware Scheduler          │
│  Multilingual Manager        │  Sync & Connectivity Manager       │
├──────────────────────────────────────────────────────────────────┤
│  Memory System (8 مخازن)     │  Skill Registry  │  Tool Registry   │
│  Model Registry              │  Benchmark Store │  Audit Log        │
├──────────────────────────────────────────────────────────────────┤
│  Adapters: LLMProvider · VectorStore · Database · SearchEngine ·  │
│            Trainer · ComputeBackend · Embedder · Translator        │
└──────────────────────────────────────────────────────────────────┘
```

### قواعد البنية

- **Core** مكتوبة بلغة قابلة للنقل (Kotlin Multiplatform أو Rust أو Python مع طبقة ربط). يجب أن تعمل على الهاتف وعلى الخادم.
- كل اعتماد خارجي يمر عبر **Adapter** له واجهة ثابتة. استبدال النموذج اللغوي أو قاعدة البيانات أو محرك البحث أو نظام التدريب يكون باستبدال الـ Adapter فقط.
- **ComputeBackend** يحدد مكان التنفيذ: `on_device` أو `user_server` أو `cloud`. يمكن نقل أي مهمة تعلم ثقيلة إلى خادم أقوى مع نقل صلاحيات المستخدم وحدود خصوصيته معها.
- كل الوحدات تكتب في **Audit Log** موحّد غير قابل للتعديل (append-only).

## 2. محرك التعلم المستمر (Continual Learning Engine)

وحدة مستقلة تدير دورة التعلم التالية بلا نهاية زمنية مفروضة، مع احترام الإعدادات والموارد:

| # | المرحلة | المخرج |
|---|---------|--------|
| 1 | مراقبة نتائج المهام السابقة | `TaskOutcome` لكل مهمة (نجاح/فشل، زمن، تكلفة، تقييم المستخدم) |
| 2 | اكتشاف الأخطاء والفجوات | `Gap` مع تصنيف وأمثلة فشل |
| 3 | تشخيص نوع الحاجة | معرفة / مهارة / أداة / استراتيجية / تكييف نموذج / تعلم من نموذج آخر |
| 4 | إنشاء هدف تعلم قابل للقياس | `LearningGoal` (مقياس، خط أساس، هدف رقمي، ميزانية، موعد) |
| 5 | جمع البيانات | أمثلة مصرّح بها، ملفات محلية، مصادر موثوقة (عند الاتصال)، مخرجات نماذج معلّمة |
| 6 | تحويل الخبرة إلى قدرة مرشحة | `Candidate` (معرفة / إجراء / أداة / استراتيجية / محوّل LoRA) |
| 7 | اختبار على أمثلة منفصلة | فصل صارم بين `dev_set` و`held_out_set` |
| 8 | قياس التحسن مقابل خط الأساس | فرق الأداء + فاصل ثقة إحصائي |
| 9 | فحص التأثير في المهارات السابقة | تقرير Regression |
| 10 | القرار | قبول / رفض / قبول مشروط بموافقة المستخدم / تراجع |
| 11 | التسجيل وتحديث الخطة | سجل في Evolution Ledger + تحديث `LearningPlan` |
| 12 | إعادة الدورة | عند ظهور فجوة جديدة أو انخفاض أداء |

### شروط إلزامية

- كل `Gap` له **أولوية** تحسبها الوحدة 9 (المجدول).
- لا يُعتمد `Candidate` إذا كانت عيّنة الاختبار أصغر من حد أدنى قابل للضبط (مثلًا 30 مثالًا)، أو إذا لم يتجاوز التحسن حد الدلالة الإحصائية.
- عند فشل هدف التعلم ثلاث مرات متتالية (قيمة قابلة للضبط) يُجمَّد الهدف ويُعرض على المستخدم، ولا يتكرر تلقائيًا.

## 3. أنواع التطور الستة (افصل بينها دائمًا)

كل تغيير في النظام يُوسم بنوع واحد بالضبط:

| النوع | الوصف | أين يُخزَّن | كيف يُختبر |
|-------|-------|-------------|------------|
| **A. Knowledge Growth** | معلومة جديدة مع المصدر والتاريخ ومستوى الثقة | Semantic Memory | أسئلة تحقق + كشف تعارض |
| **B. Skill Acquisition** | إجراء قابل لإعادة الاستخدام مع شروط الاستخدام | Skill Registry | اختبارات وحدة + مهام held-out |
| **C. Tool Evolution** | أداة جديدة (كود/سكربت/استدعاء API) | Tool Registry | تشغيل في Sandbox + اختبارات أمان |
| **D. Strategy Improvement** | أسلوب حل أفضل (تخطيط، تفكيك، تحقق ذاتي، اختيار نموذج) | Strategy Store | مقارنة A/B على مهام متطابقة |
| **E. Model Adaptation** | تكييف أوزان نموذج محلي (LoRA, QLoRA, fine-tuning, DPO) | Model Registry | Benchmarks كاملة + فحص النسيان |
| **F. Cross-Model Learning** | معرفة أو مهارة أو بيانات تدريب مكتسبة من نموذج ذكاء آخر | حسب ناتجها (A–E) + سجل المصدر | مثل نوع الناتج + تحقق من صحة المعلّم |

**ممنوع**: عرض النوع A أو B على أنه "النموذج أصبح أذكى". التقارير تقول بدقة: "أُضيفت 12 معلومة"، "اعتُمدت مهارة جديدة رفعت النجاح من 61% إلى 78% على 50 مهمة غير مرئية"، وهكذا.

## 4. التعلم من نماذج الذكاء الأخرى (Multi-Model Learning Hub)

وحدة مستقلة تتيح لـ MOSAIC الاستفادة من نماذج ذكاء اصطناعي أخرى (سحابية أو محلية أو متخصصة) بوصفها **معلّمين ومستشارين ومقيّمين**، دون الاعتماد الدائم عليها.

### 4.1 سجل النماذج (Model Registry)

لكل نموذج خارجي أو محلي سجل يتضمن:

- المعرّف، المزوّد، الإصدار، نوع الوصول (API / محلي / خادم المستخدم).
- القدرات المعلنة والقدرات **المقاسة فعليًا** لكل مجال ولغة.
- التكلفة لكل طلب أو رمز، زمن الاستجابة، حدود الاستخدام.
- **شروط الترخيص والاستخدام**: هل تسمح شروط المزوّد باستخدام المخرجات في تدريب نماذج أخرى؟ (حقل إلزامي: `allows_training_on_outputs: yes/no/unknown`).
- سياسة الخصوصية: هل يجوز إرسال بيانات المستخدم إليه؟
- سجل الدقة التاريخي (كم مرة كان محقًا عند التحقق).

النظام لا يضع حدًا لعدد النماذج المسجّلة. إضافة نموذج جديد = إضافة سجل + Adapter.

### 4.2 أنماط التعلم من النماذج الأخرى

| النمط | الوصف | الناتج |
|-------|-------|--------|
| **Consultation** | طلب رأي نموذج أقوى في مهمة صعبة عند الحاجة | حل المهمة + تسجيل الحالة للتعلم لاحقًا |
| **Teacher → Student Distillation** | توليد أمثلة وشروحات وسلاسل حل من نموذج معلّم لتدريب نموذج محلي أصغر | مجموعة بيانات تدريب (نوع E) |
| **Skill Extraction** | ملاحظة كيف يحل النموذج المعلّم فئة مهام وتحويل الأسلوب إلى إجراء مكتوب | مهارة (نوع B) أو استراتيجية (نوع D) |
| **Model-as-Judge** | استخدام نموذج أو أكثر لتقييم مخرجات MOSAIC | إشارات تقييم (مع معايرة دورية مقابل تقييم بشري) |
| **Ensemble & Debate** | عرض المسألة على عدة نماذج ومقارنة الإجابات والوصول إلى إجماع أو كشف الخلاف | إجابة أدق + كشف نقاط عدم اليقين |
| **Capability Routing** | تعلم أي نموذج هو الأفضل لأي نوع مهمة بناءً على النتائج الفعلية | سياسة توجيه (نوع D) |
| **Knowledge Harvesting** | استخلاص معارف من نماذج متخصصة (طب، قانون، برمجة) مع وسمها بمستوى ثقة | معرفة (نوع A) تحتاج تحققًا |

### 4.3 قواعد إلزامية للتعلم من النماذج

1. **المعلّم ليس مرجعًا مطلقًا**: كل ما يأتي من نموذج آخر يُوسم `source: model:<id>` ويبدأ بمستوى ثقة متوسط. لا يُرفع إلا بالتحقق (اختبار، مصدر موثوق، إجماع مستقل، تأكيد بشري).
2. **احترام الترخيص**: لا تُستخدم مخرجات نموذج في تدريب أوزان (نوع E) إذا كان `allows_training_on_outputs` ليس `yes`. في هذه الحالة يُسمح فقط بالاستشارة والتقييم المؤقت حسب شروط المزوّد.
3. **الخصوصية**: لا تُرسل بيانات المستخدم الخاصة إلى نموذج خارجي إلا إذا وافق المستخدم على ذلك النموذج تحديدًا. البديل: إخفاء الهوية (Redaction) أو استخدام نموذج محلي.
4. **هدف الاستقلال التدريجي**: يقيس النظام نسبة المهام التي احتاج فيها إلى نموذج خارجي لكل فئة. الهدف خفض هذه النسبة مع الحفاظ على الجودة، أي أن MOSAIC يتعلم ولا يعتمد فقط.
5. **كشف تلوث البيانات**: أمثلة التقييم held-out لا تُرسل أبدًا إلى نموذج معلّم يُستخدم في توليد بيانات التدريب.
6. **كشف أخطاء المعلّم**: عند تعارض نموذجين أو تعارض نموذج مع مصدر موثوق، تُسجّل الحالة في ذاكرة التعارضات ولا يُعتمد أي منهما تلقائيًا.
7. **الميزانية**: كل استدعاء لنموذج خارجي يمر عبر المجدول (الوحدة 10) ويُحسب في التكلفة.

### 4.4 التخرج: الاستقلال التام عن المعلّم (Graduation)

الهدف النهائي من التعلم من النماذج الأخرى أن **يستغني MOSAIC عنها**. المعلّم مرحلة مؤقتة لكل فئة مهام:

1. **مرحلة التعلم**: المهام التي لا يعرفها MOSAIC تذهب للمعلّم. يحفظ MOSAIC الإجابات ويحوّلها إلى مهارات ومعرفة خاصة به.
2. **مرحلة الإثبات**: تُختبر قدرات MOSAIC وحده (بدون المعلّم) على أمثلة مستقلة لم يرها المعلّم.
3. **التخرج**: عندما تصل دقة MOSAIC المستقلة إلى العتبة (مثلًا 95%) ولا تقل عن دقة المعلّم المقاسة إلا بهامش صغير، تُعلَّم الفئة "مستقلة". **لا يُستدعى المعلّم لها بعد ذلك أبدًا**، وتعمل بالكامل محليًا وبدون إنترنت.
4. **بعد التخرج**: يستمر التعلم من البشر ومن الخبرة الذاتية فقط. إعادة السماح بالمعلّم لفئة متخرجة قرار يتخذه المستخدم يدويًا، ولا يحدث تلقائيًا.
5. **اللوحة** تعرض لكل فئة: نسبة الاعتماد على المعلّم مع الزمن، وحالة التخرج، ودقة MOSAIC مقابل دقة المعلّم.

### 4.5 مقياس نجاح هذه الوحدة

- تحسن أداء MOSAIC **دون** النموذج المعلّم على مهام held-out بعد التعلم منه.
- انخفاض نسبة الاعتماد على النماذج الخارجية لكل فئة مهام مع الوقت.
- دقة المعلّمين المقاسة (لا المعلنة) محدّثة باستمرار.

## 5. نظام الذاكرة القابل للتوسع

### 5.1 المخازن الثمانية

| المخزن | المحتوى | حقول إلزامية |
|--------|---------|--------------|
| Semantic Memory | حقائق ومفاهيم | المصدر، التاريخ، الثقة، اللغة، صلاحية الزمن |
| Episodic / Experience Memory | ما حدث في المهام | المهمة، السياق، الخطوات، النتيجة |
| Skill Memory | الإجراءات المعتمدة | الإصدار، الشروط، الاختبارات، معدل النجاح |
| Tool Memory | الأدوات وطريقة استخدامها | الإصدار، الصلاحيات، نتائج الاختبار |
| Experiment Memory | نتائج التجارب المقبولة والمرفوضة | الفرضية، البيانات، النتيجة، القرار |
| Error & Fix Memory | الأخطاء وحلولها | نمط الخطأ، السبب الجذري، الحل، عدد التكرار |
| Preference Memory | التفضيلات المصرّح بحفظها فقط | نطاق الموافقة، تاريخ الموافقة، قابلية الحذف |
| Change & Version Log | كل تغيير في النظام | من، متى، لماذا، النوع، الإصدار السابق |

### 5.2 العمليات المطلوبة

- فهرسة مزدوجة: متجهية (Embeddings) + نصية/هيكلية.
- استرجاع هجين مع ترتيب حسب الصلة والثقة والحداثة.
- تحديث مع الاحتفاظ بالإصدار السابق.
- **إزالة التكرار** (Deduplication) الدلالي.
- **كشف التعارض**: معلومتان متناقضتان تُعلَّمان ولا تُدمجان تلقائيًا.
- **تقادم المعرفة**: كل معلومة لها `valid_until` أو `review_after`.

### 5.3 سياسات الضغط عند اقتراب حدود التخزين

بالترتيب، وكلها قابلة للتخصيص:

1. إزالة التكرار.
2. ضغط الخبرات المتشابهة في ملخصات مع الاحتفاظ بأمثلة تمثيلية.
3. أرشفة المعلومات قليلة الاستخدام (تخزين بارد / خادم المستخدم).
4. خفض دقة الـ Embeddings للأرشيف.
5. **لا حذف لمعلومات المستخدم المهمة** إلا بسياسة معلنة وموافقة صريحة. يُعرض على المستخدم ما سيُحذف قبل الحذف.

### 5.4 قابلية الاستبدال

كل مخزن خلف واجهة `MemoryStore`. التطبيق الأولي: SQLite + مكتبة متجهات محلية (مثل sqlite-vec أو FAISS). يجب أن يمكن الانتقال لاحقًا إلى PostgreSQL + pgvector أو Qdrant دون تغيير بقية النظام.

### 6.2 قواعد المختبر

- كل التجارب تعمل في **Sandbox معزول**: نسخة من الذاكرة للقراءة فقط، بلا وصول للشبكة إلا عند الإذن، بصلاحيات ملفات محدودة، بحدود CPU والذاكرة والزمن.
- الأدوات المولّدة تُفحص قبل التشغيل: تحليل ساكن، منع الاستدعاءات الخطرة، تشغيل محدود الصلاحيات.
- **تتطلب موافقة المستخدم**: أي تغيير يمس البيانات الشخصية، أو الوصول للشبكة، أو الصلاحيات، أو تكلفة مالية فوق حد معيّن، أو تكييف أوزان نموذج، أو مخاطرة `high`.
- النشر تدريجي: `candidate → shadow mode → canary (نسبة من المهام) → active`.
- التراجع بأمر واحد وفوري، وأيضًا تلقائي إذا انخفض الأداء الحي عن حد معيّن.

---

## 7. منع التدهور والنسيان الكارثي (Regression & Forgetting Guard)

- **Regression Testing**: كل مهارة معتمدة لها مجموعة اختبارات بإصدار ثابت تُشغَّل قبل كل اعتماد.
- **Replay Evaluation**: إعادة تشغيل عينة من المهام الحقيقية السابقة (المصرّح بها) على الإصدار الجديد.
- **Versioned Skill Tests**: الاختبارات نفسها لها إصدارات، ولا يُعدّل اختبار ليجعل تحسينًا ينجح.
- **Held-Out Benchmarks**: مجموعات مغلقة لا تُستخدم في التطوير ولا تُرسل إلى نماذج معلّمة.
- **مقارنة قبل/بعد** على مستوى كل مهارة وكل لغة.
- عند تدريب النماذج (نوع E): استخدم Replay Buffer، وتقنيات مثل EWC أو مزج البيانات القديمة، ومحوّلات LoRA منفصلة لكل مجال بدل تعديل الأوزان الأساسية، مع إمكانية فصل المحوّل فورًا.

**قاعدة القبول**: التحسين يُقبل فقط إذا:
1. حسّن الأداء على held-out بفارق ذي دلالة إحصائية.
2. لم يخفض أي مهارة حرجة بأكثر من حد مسموح (مثلًا 2%).
3. كانت تكلفته ضمن الميزانية.
4. لم ينجح في مهمة واحدة فقط، بل على عينة كافية.

---

## 8. التعلم أثناء الاتصال والانقطاع

### Online
- البحث عن معارف حديثة من مصادر موثوقة مع تسجيل الرابط والتاريخ.
- استكشاف أدوات ومكتبات ونماذج جديدة.
- استشارة النماذج المعلّمة (حسب الموافقات).
- طلب حوسبة خارجية للتدريب عند الموافقة.

### Offline
- التعلم من الملفات المحلية المصرّح بها.
- تحليل نتائج المهام السابقة وتنظيم الذاكرة.
- إنشاء مهارات واختبار أدوات محليًا.
- تشغيل نماذج محلية صغيرة للتقييم والتعلم.
- متابعة التجارب التي لا تحتاج إلى الإنترنت.
- وضع المهام التي تحتاج اتصالًا في **قائمة انتظار**.

### المزامنة عند عودة الاتصال
- مزامنة السجلات المسموح بها فقط.
- حل التعارضات بقواعد واضحة (الأحدث + الأعلى ثقة + عرض الحالات الغامضة على المستخدم).
- **لا رفع تلقائي للبيانات الخاصة.**
- **ممنوع** الادعاء باكتساب معلومة من الإنترنت أثناء الانقطاع. كل معلومة تحمل حقل `acquired_mode: online|offline`.

---

## 9. التعلم من البشر (Human Feedback Learning System)

- واجهات: تصحيح، تقييم (نجوم/إبهام)، مقارنة إجابتين، اقتراح تحسين، تعليم مهارة بالأمثلة.
- **تصنيف الملاحظة** إلزاميًا:

| التصنيف | المعالجة |
|---------|----------|
| ملاحظة جديدة | تُخزّن بثقة متوسطة |
| تصحيح موثوق | يُطبَّق ويُنشئ اختبار Regression جديد |
| رأي شخصي | يُخزّن تفضيلًا للمستخدم فقط ولا يصبح حقيقة |
| معلومة تحتاج تحققًا | تدخل طابور التحقق |
| بيانات غير موثوقة أو متعارضة | تُعزل وتُعلَّم |

- **عزل المستخدمين**: بيانات كل مستخدم في نطاق منفصل. ما يتعلمه النظام من مستخدم لا ينتقل إلى مستخدم آخر إلا بموافقة صريحة وبعد إزالة الهوية.
- لا تدريب مشترك على المحادثات الخاصة دون موافقة صريحة وسياسة خصوصية منشورة.
- الحماية من التسميم: حدود لتأثير مستخدم واحد، وكشف أنماط التلاعب.

---

## 10. التعلم متعدد اللغات (Multilingual Manager)

- محركات لغوية قابلة للتبديل لكل لغة أو لهجة (فصحى، لهجات عربية، إنجليزية، ...).
- **مجموعة تقييم منفصلة لكل لغة** تقيس: الفهم، التلخيص، الترجمة، اتباع التعليمات، الكتابة.
- جدول مستوى لكل لغة: `unsupported → experimental → beta → supported`. الترقية تتطلب نتائج تقييم فوق حدود معلنة.
- **ممنوع** ادعاء إتقان لغة دون أدلة تقييم.
- إضافة لغة جديدة = إضافة سجل + بيانات تقييم + محرك، دون تعديل النواة.

---

## 11. المجدول الواعي بالموارد (Resource-Aware Learning Scheduler)

### معادلة الأولوية (قابلة للضبط)

```
priority = (importance × frequency × failure_rate × expected_gain × user_weight)
           / (estimated_cost + ε)
```

حيث `estimated_cost` يجمع: الحوسبة، الذاكرة، التخزين، البطارية، بيانات الشبكة، تكلفة النماذج الخارجية.

### القواعد
- لا تعلم ثقيل إلا والجهاز يشحن (افتراضيًا)، وعلى Wi-Fi، وبطارية فوق حد معيّن، وحرارة طبيعية.
- حدود يحددها المستخدم: ميزانية مالية شهرية، حجم بيانات، تخزين، وقت تشغيل يومي.
- دعم: **الجدولة، الإيقاف المؤقت، الاستئناف، الإلغاء** لأي مهمة تعلم، مع حفظ نقاط استئناف (Checkpoints).
- **شرط توقف إلزامي**: إذا لم تُظهر دورة تعلم تحسنًا قابلًا للقياس بعد ميزانية معيّنة، تتوقف وتُسجّل كـ "غير مجدية حاليًا".
- نقل المهام الثقيلة تلقائيًا إلى خادم المستخدم أو السحابة عند الموافقة.

---

## 12. لوحة إثبات التطور (Evolution Dashboard)

تعرض بوضوح، مع إمكانية التصفية حسب الفترة واللغة والمجال:

- المهارات المكتسبة (مع الإصدار ونسبة النجاح).
- الأدوات الجديدة ونتائج اختبارها.
- التحسينات المعتمدة والمرفوضة والمتراجع عنها، مع السبب.
- نسبة نجاح المهام قبل التحسين وبعده.
- الأداء على مهام **غير مستخدمة في التطوير** (held-out).
- **المهارات التي تراجع أداؤها** (بلون تحذيري).
- مصادر المعرفة (مواقع، ملفات، بشر، **نماذج أخرى**) ومستوى الثقة.
- **لوحة النماذج المعلّمة**: ما تعلّمه MOSAIC من كل نموذج، ودقة كل معلّم المقاسة، ونسبة الاعتماد الخارجي مع الزمن.
- استهلاك الموارد والتكلفة.
- عدد التجارب الناجحة والفاشلة.
- **التغييرات التي تنتظر موافقة المستخدم** (مع زر قبول/رفض).

**ممنوع** عرض عدد الذكريات أو الأدوات كدليل على الذكاء. المقياس الرئيسي هو الأداء على مهام مستقلة قابلة للتكرار.

---

## 13. قابلية التوسع المستقبلي

- واجهات ثابتة لـ: `LLMProvider`, `Embedder`, `VectorStore`, `Database`, `SearchEngine`, `Trainer`, `ComputeBackend`, `Translator`, `SandboxRuntime`.
- البداية: تطبيق **Android** (Kotlin + Jetpack Compose للواجهة)، والنواة منفصلة تمامًا عن الواجهة.
- نموذج محلي صغير على الجهاز (عبر llama.cpp أو MediaPipe LLM أو ONNX Runtime) + نماذج سحابية عبر Adapters.
- إمكانية تشغيل النواة نفسها على خادم (Linux/Docker) ومزامنتها مع الهاتف بتشفير طرفي.
- نظام إضافات (Plugins) لإضافة مهارات وأدوات ونماذج من مصادر خارجية بعد اختبارها في Sandbox.

---

## 14. الأمان والخصوصية

- تشفير البيانات على الجهاز (Android Keystore) وأثناء النقل.
- نطاقات صلاحيات دقيقة لكل أداة ومهارة.
- قائمة موافقات قابلة للمراجعة والسحب في أي وقت.
- تصدير وحذف كامل لبيانات المستخدم بطلبه.
- منع تنفيذ أدوات مولّدة ذاتيًا خارج الـ Sandbox.
- لا مفاتيح API في الكود؛ تُخزّن في مخزن آمن.

## 15. خطة التنفيذ على مراحل

| المرحلة | المحتوى | معيار الإنجاز |
|---------|---------|----------------|
| **P0 — الأساس** | الواجهات، Audit Log، Memory System (SQLite + vectors)، LLMProvider Adapter، Task Executor | تنفيذ مهمة وتسجيل نتيجتها |
| **P1 — القياس** | Benchmark Store، dev/held-out، Regression Runner، Dashboard أولي | قياس خط أساس لـ 3 مهارات |
| **P2 — دورة التعلم** | Continual Learning Engine (أنواع A, B, D)، Evolution Lab، Sandbox | أول تحسين معتمد مثبت على held-out |
| **P3 — التعلم من البشر والنماذج** | Human Feedback System، Multi-Model Learning Hub (Consultation, Judge, Routing, Skill Extraction) | تحسن مثبت مصدره معلّم خارجي + انخفاض الاعتماد عليه |
| **P4 — الأدوات والموارد** | Tool Evolution (C)، Resource Scheduler، Offline/Online Sync | أداة مولّدة ذاتيًا معتمدة + تعلم Offline |
| **P5 — تكييف النماذج** | Trainer Adapter، LoRA، Distillation، Forgetting Guard | محوّل LoRA يحسّن مجالًا دون تراجع غيره |
| **P6 — اللغات والتوسع** | Multilingual Manager، نقل الحوسبة لخادم، Plugins | دعم لغة جديدة بتقييم معلن |

## 16. معيار النجاح الأساسي

يُعد MOSAIC قد أحرز تقدمًا حقيقيًا عندما يستطيع، **دون تدخل برمجي يدوي**:

1. **اكتشاف** قصور في أدائه من نتائج فعلية.
2. **اكتساب** قدرة جديدة أو تحسين قدرة قائمة (ذاتيًا، أو من البشر، أو من نماذج أخرى).
3. **إثبات** تحسن أدائه على مهام مستقلة لم تُستخدم في التطوير، بنتائج قابلة للتكرار.
4. **الاحتفاظ** بالتحسين بصورة قابلة للمراجعة والتراجع، دون تدهور القدرات السابقة.

---

## 17. المطلوب منك الآن (مخرجات التسليم)

1. **وثيقة معمارية** تفصيلية لكل وحدة، مع الواجهات (Interfaces) ونماذج البيانات.
2. **مخطط قاعدة البيانات** للمخازن الثمانية والسجلات (Improvement, Model, Skill, Tool, Benchmark).
3. **هيكل المشروع** (مجلدات ووحدات) للنواة وتطبيق Android والخادم.
4. **تنفيذ المرحلة P0 ثم P1** بكود يعمل واختبارات آلية.
5. **مثال عملي كامل لدورة تعلم**: فجوة مكتشفة → هدف → مرشح → اختبار held-out → قرار → ظهوره في اللوحة.
6. **مثال عملي للتعلم من نموذج آخر**: استشارة معلّم → استخلاص مهارة → اختبارها دون المعلّم → قياس انخفاض الاعتماد.
7. قائمة بالمخاطر والقيود المعروفة، بصراحة.

> **المبدأ النهائي**: MOSAIC يتعلم باستمرار، ويتطور بطريقة قابلة للقياس، ويكتسب قدرات جديدة من خبرته ومن البشر ومن نماذج الذكاء الأخرى، دون إعادة برمجة يدوية في كل مرة. كل قدرة جديدة تُختبر قبل اعتمادها، ولا سقف مصطنعًا لما يمكنه تعلمه، مع الصدق التام بشأن حدود الموارد.
